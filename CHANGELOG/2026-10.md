# Change Log — October 2026

One line per change: date, title, requester, the *intent* behind the ask (not a verbatim
quote), what actually changed, and the commit hash(es). Newest at the top. See `CHANGELOG.md`
for the format note and index of other months.

- **2026-10-04** One Google sign-in across all internal tools (Sharath) — having to sign in again on every internal page was the main annoyance and a barrier to treating the tools as one interface; the photo pool, WhatsApp inbox, event payments and accommodation calendar now use the same stored sign-in as `/internal`, `/internal/access` and `/internal/security` (one line each), so signing in once opens them all and "use a different account" signs out of all; each tool still checks its own role on the server on every request. Google's roughly one-hour token expiry and the per-tab storage are unchanged. 20 end-to-end checks over the four built pages, including that a sign-in left under an old key is ignored. `aeeaed1`, `92000ff`
- **2026-10-04** Access screen and `/internal` landing page (Sharath) — roles could only be changed with SQL, and each internal tool needed its own URL; added `/internal/access` (super admins: people shown by name with their role and what it allows in words, give/change/remove roles incl. accommodation booking-type limits, add a person, deactivate/reactivate, activity log; read-only until a second factor is entered on the page) and `/internal` (sign in once, see the tools you hold a role in, plus Access and Security for super admins) with a small `staff-me` endpoint that returns no email; the three new pages share one sign-in and step-up per tab. Tested end to end with the built pages in a simulated browser against the real functions (64 checks, plus deliberate breakages caught); the four older tools are untouched and keep their own sign-in (issue #89). `07fbfeb`, `6454e7e`
- **2026-10-04** Access module API (Sharath) — who can do what had to be changed by hand in the database; added `staff-admin` for super admins only: list people and roles, activity feed, add a person, set or remove a module role, deactivate or reactivate, where every change needs two enrolled second-factor methods plus a fresh step-up, is audit-logged before it is made (refused if the log can't be written), never returns an email, never deletes anyone and cannot create or remove super admins. Also moves the MFA queries to a shared store and adds role descriptions and the booking-type list to the registry. `50deb53`, `d3ec06a`
- **2026-10-04** Fix the high-severity Dependabot alert on `http-cache-semantics` (Sharath) — GitHub kept flagging a high-severity alert (GHSA-ch52-4w7c-c8xp) on a package Astro pulls in; checked the brand-new 4.3.0 release against the real upstream commit and read its whole diff, then bumped `http-cache-semantics` to 4.3.0 and `fast-uri` to 3.1.8 in the lockfile only (the site was not practically exposed: both are build/lint-time, not in the deployed site). The alert closed itself; six dev-tooling advisories with no upstream fix remain (`stylelint → fast-glob → micromatch → braces`). `a70c293`, `1185fb5`
- **2026-10-04** QR code for authenticator setup (Sharath) — typing a long setup key into an authenticator app is slow and error-prone; the security page now shows a QR code to scan, drawn in the browser (the secret never goes to an online QR service) with the typed key and an `otpauth://` link kept as fallbacks, and the secret and QR are wiped from the page when setup ends. Adds one dependency, `qrcode-generator` (MIT, zero dependencies); decoding the drawn code with an independent QR reader returns the exact setup link. `f227a47`, `127421c`
- **2026-10-04** Super-admin second factors: authenticator app, recovery codes, `/internal/security` (Sharath) — two of the three super admins sign in with personal Gmail accounts, so Workspace 2-step verification can't protect the tools that will manage access; added step-up authentication ahead of the Access module (which is deferred): TOTP with AES-GCM-encrypted secrets, ten single-use recovery codes stored only as hashes, ten-minute signed step-up tokens, five-wrong-codes lockout, atomic replay protection, reset by a second super admin, all audit-logged, plus migration `0029` (three tables). Nothing requires it yet and it needs `STAFF_MFA_KEY` set in Netlify to work; losing that key invalidates every authenticator and recovery code at once (issue #89). `fb0e118`, `4400ba7`, `db416f1`
- **2026-10-04** Fill an empty staff name from the Google account on first sign-in (Sharath) — the staff table had no names and the Access module needs people shown by name, not email; the first time an authorized person signs in with an empty name it is copied from their Google profile, guarded so an existing name is never overwritten. `1531732`, `051c4ef`
- **2026-10-04** WhatsApp reply signature falls back to the Google name, then a masked address (Sharath) — if no signing-as name is typed the reply used to go out unsigned; now it tries the registered staff name, then the name on their Google account, then a masked address like `a••••@gmail.com`, never the full email, and the masker caps its dots so the length isn't revealed. `7602b39`, `4f7d2db`
- **2026-10-04** Accommodation calendar migrated onto the staff roles, guest contact details made write-only (Sharath) — the last internal tool still gated by a Google Sheet, and its guest form held every saved guest's real mobile and email in the browser behind a cosmetic mask; now `view` reads the calendar and `edit` writes it (the old admin / restricted / viewer roles map to admin / user-with-allowed-types / read-only), saved guests' mobile and email never reach the browser ("On file (hidden)" with a Replace button, typeahead shows a short `#ref` tag, and saving without touching them keeps the stored values), read-only roles get masked names and no preferences, and bookings record the staff id instead of an email. Both Sheet allow-lists are now unused (issue #89). `fd8c838`, `7a90300`
- **2026-10-04** Event-payments admin migrated onto the staff roles (Sharath) — the next module off the shared Sheet allow-list, and its dashboard exposed every payer's email and phone and let anyone on the Sheet issue refunds; now `view` reads bookings and only admins can refund (single or whole-event), payer email/phone no longer reach the browser (name masked for read-only, "On file (hidden)" in the detail panel), the staff id replaces their email in `refunded_by` and in the note stored on each Razorpay refund, and every refund is audit-logged before any money moves and refused if the log write fails. Accommodation is the last module still on a Sheet (issue #89). `41c6035`, `229b1b5`
- **2026-10-04** Hotfix: staff lookup broke photo-pool and WhatsApp (Sharath) — right after the staff-roles change shipped, both internal pages failed to load for everyone; the role lookup embedded `staff_module_roles` in a `staff_users` query, which PostgREST rejects as ambiguous (two foreign keys between the tables), so every request returned a server error. Replaced it with two plain queries and made the test mock reject such embeds. `03b2a3b`, `2b36e17`
- **2026-10-04** Per-module staff roles for the internal admin tools, photo-pool and WhatsApp migrated (Sharath) — several internal pages each carried their own Sheet allow-list, and not everyone should reach every module or see guest contact details; added Supabase staff access tables (super admin / admin / user / read-only roles, append-only audit log) with a shared `requireStaff` helper, backfilled everyone from the old Sheets, and moved photo-pool and WhatsApp onto it with server-side masking (WhatsApp phone numbers and photo uploader emails no longer reach the browser, names masked for read-only, reply signature no longer falls back to the staff email). Event-payments and accommodation still use their Sheets; shell page, step-up auth and encryption still to come (issue #89). `69b93a2`, `75f8a34`, `1ac94d3`, `8f84f3b`
